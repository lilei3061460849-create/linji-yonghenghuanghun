# 法术统一流程架构方案（设计稿，待规则确认）

本稿依据仓库代码、规则正文和测试的已核查部分，以及用户本轮五项决策制定；不是功能已实现的声明，也不声称完成全仓穷尽式审查。本轮只写设计，不修改战斗代码或规则事实源。`spell_program.py` 是此前提交的静态结构草案，尚非下述完整方案，更未接入生产执行。

## 1. 目标与不变量

对外提供单一施法行动；逻辑基础为已有道纹动作、条件、流程控制和事件。顺序是默认边，分支和重复由条件及边构成；循环区域及其上下文只属于编译/执行内部元数据，不向玩家暴露 LoopStep。所有实际动作继续调用 `engine/combat_parts/spells.py` 的法术单步结算核心及既有道纹前置、资源支付和伤害机制；不能由图解释器直接更改状态。主动/反应路径的 `SpellStepPolicy`、行动支付、反应窗口、顺序、阶数、目标、X、异常与中断、X=0 及原有定义生命周期都保留，除非用户另作规则裁定。

现有 `use_daowen`、`define_spell` 和 `cast` 的兼容入口不可在迁移中删除；面向玩家的统一入口是独立后续阶段，转接后也需保持同样的参数校验、事务回滚、束缚和决斗优先权。仅合并展示不能称作底层统一。

## 3. 描述层、图结构与旧 DSL 迁移

程序定义 = 稳定 `program_version/program_id` + 启动配置（瞬发或既有合法事件、持有者/角色与触发上下文）+ 有序节点表 + 显式入口 ID + 旧源映射和版本化编译元信息。ID 由定义提供或编译器依据旧 AST 持久生成，**一旦签发不可因插入而重编号**；旧 AST 的路径仅作为首次转换的兼容映射，不承诺重新编译不同文本得到相同 ID。禁止重复/空 ID、缺失目标、非法节点/条件与无法确定的流程，完整验错且不改战斗状态。

- 动作节点：`{id, action: 现有 ActionStep 或等价类型, next?}`；声明目标角色及决策槽映射，未设 next 即后继。执行时依现有 policy、实际角色/目标和 StepRequest 调用单步结算；动作完成、闪避、跳过、失败、中断分别沿原协议处理。空档/支付仍由原调度负责。
- 条件节点：`{id, expression: 现有 Cmp/BoolOp/Not AST, true?, false?, policy}`；两边均指合法节点或定义为默认后继，分支可汇合、跳过任意范围、嵌套或回跳。表达式和可读取字段仍经现有 resolver、事件身份与合法性校验。
- 跳转/终止：`{id, target}` 或结束；无条件跳转亦经同一图边转移与循环/窗口限制。默认顺序是显式编译得到的后继边，图构建后运行时不按数组下标算跳过数。
- 事件等待：`{id, event_selector, resume}` 仅接入实际已接线的事件源、合法身份与既有窗口策略；事件名称、主体和上下文可匹配，等待不合成事件、不支付道纹成本。事件是否到达、被既有重入策略抑制以及该等待是否可恢复由事件层判定，不能单靠程序计数器强行继续。可监听范围、取消与事件投递规则见待确认项。

迁移表：

| 旧组件 | 新表示 | 必须保留的元数据 |
|---|---|---|
| 顺序 ActionStep | 动作节点 + 默认顺序边 | DFS 槽号、目标角色、X/闪避/附加决策和步骤日志 |
| IfStep（含嵌套、空否则） | 条件节点 + 真/假边 + 汇合目标；空分支直达汇合 | `_index_ifs` 旧路径到节点 ID 映射、条件首次选择、冻结范围、两臂槽顺序 |
| LoopStep/`循环N次` | 普通回边 + 编译产生的内部循环区域 | 旧体边界、前置 `spell_loop_guard`、每轮快照、定次/请求上限较小者、已执行数、工程阀、循环结果及日志轮号；**不是无条件无限跳转** |
| tuple 内置流程 / `loop=True` | 兼容适配到动作/边；已有定义的触发配置原样保留 | 旧内置定义、完成顺序、循环停条件、旧 flow 的决策布局 |
| 触发时机 / 瞬发 | 注册于既有触发层 / 主动入口 | 时机接线状态、持有者、来源、调用策略及事件上下文 |
| `SpellCastRequest` | 同一动作节点映射槽，沿用一次提交一槽 | 未走分支也保留槽，循环各轮沿用对应决策；`max_iterations`、`source`、branch_snapshot |
| 阶数 | 基于源级语义的静态元数据 | 触发算一重，瞬发不算，动作每处一次、两分支均计，循环回边不计；不能按运行步数/编译插入的跳转数计算 |

迁移先在影子编译中比对旧 AST 和 CFG 的动作/分支/循环/日志映射；生产始终只用一个可观察的 `SpellExecution` 路径。只有所有受影响调用者（schema、条件预测、目标、协力、自动决策、校验、档案、AI）接入 IR 且差分通过后，才移除旧 AST 执行解释；不能永久并行两套互不兼容执行系统。

## 4. 条件、执行位置与普通跳转

帧包含 program 版本/hash、当前节点 ID、步骤决策及其源、施法者/事件身份引用、policy、执行状态、中断原因、提交冻结表、每次判断轨迹、循环上下文栈、已执行结果、等待令牌和反应/空档上下文。执行器按当前节点取指，检查施法者仍可行动及既有前置，只有动作节点执行效果。一个节点执行完后转移 PC；失败保留原规定的已发生结算，非法图在执行前拒绝。动作消耗及窗口/中断不能由跳转或条件节点重复触发。

动态条件每次到达节点，读取当时规定的 `GameState` 和本次合法事件上下文，条件再到达则重新计算。冻结条件按**提交和执行实例**实现现有语义：启动实例时取得提交中已有的冻结映射；映射已有的节点直接使用，未有的节点在本次执行中每次动态求值，同时只记该节点的首次结果；执行结束将首次结果填入该提交以供后续命中复用。冻结表的来源、归属和生存期沿用同一 decision 的现行语义，不扩大到所有事件或整个战斗。事件完成顺序与触发提交的归属不因节点跳转改变。

## 5. 控制流图、复杂循环与轮次：修订设计

**不将严格嵌套作为语言上限。** 图仍是节点 ID 与明确边；编译器使用可达性、强连通分量（SCC）、支配关系、回边和包含关系分析，识别独立、嵌套、多回边和交叉循环。SCC 只证明区域内部节点互相可达，不足以唯一划定“每一轮”；支配节点和自然循环也不能覆盖所有多入口/不可归约图。因此不能仅因不可归约或区域交叉就拒绝，也不能靠源码顺序、节点 ID 排序或 DFS 访问顺序暗中决定游戏轮次。

计划采用**静态区域分析 + 运行时按实际路径记录轮次**：编译器输出 SCC、候选入口/回边/退出边、节点所属的重叠区域，以及版本化、可复现的轮次边界元信息；执行帧维护每个活动轮次的入口、来源边、开始快照、动作计数和当前轨迹。对于多入口或交叉区域，编译器先尝试从边和可追踪路径确定每次重新进入的入口与对应闭合路径；同一节点可以属于多个活动区域，不能强制压成单一栈或只记录一个快照。多个回边共享同一入口时，不因为回边来源不同而凭空创建额外轮次。不同入口、重叠路径可并存，按明确的闭合/退出次序对相关上下文分别比较。

**仍待确定的设计边界：** 对同一条实际路径存在多种有效环分解时（例如 A→B→C→B→D→A，同时 A→B→C→D→A 亦有边），单靠图论没有唯一的游戏规则“一轮”定义。至少需明确轮次关联哪个入口、多个活动区域同时闭合的次序及是否对部分路径重复计数。不能把某个图论算法的结果当成规则事实。本稿提出下述**候选语义**供确认，待裁定/证明后再承诺接入；结构本身可确定处理时应支持，而非按“交叉/多入口”类别一概拒绝。若候选语义仍无法给某图确定唯一记录顺序或不能证明不漏/重复检查，编译器返回含节点、边、冲突解释的诊断；资源耗尽和工程安全阀不属于语义无定义，不能因潜在无限循环就拒绝合法图。

### 候选轮次协议（新图；旧 DSL 兼容仍按旧执行器顺序）

1. **进入及轮初**：进入可识别循环入口、且前置条件决定实际进入循环体后，在任何本轮动作前记录起始指纹和执行数。入口条件不成立直接退出、循环体一次未进入，不虚构零进展轮。
2. **返回入口**：沿经编译识别的回边再次到达该活动入口前，以当下战场为本轮终点；先对闭合的循环上下文依确定顺序检查，再决定是否进入新一轮并取新的起始快照。指纹相等或本轮未实际执行动作时，按现有 `NO_NET_CHANGE` 中断；完成/闪避视作已执行、跳过不视作已执行（与现有 `_executed_count` 相同）。
3. **正常退出/提前跳出**：提议当边离开已进入的循环区域时，先以离开前状态终结该活动轮并检查；通过后释放上下文、再执行区域外节点。连续退出多个区域时从最内/最具体到外层；重叠但非包含的区域需明确可复现次序。此项是**新图拟议扩展**，不声称旧规则已涵盖任意 break；未通过裁定前不改变旧行为。
4. **等待事件/对手空档**：暂停不结束轮、不触发净变化检查；保留轮初快照、PC 和等待令牌，合法事件到来恢复同一轮。候选口径是轮末比较暂停前轮初与恢复后轮末的真实战场，因此等待期间其他角色造成的变化也会被计入；这与“比较战场状态”字面相符，但旧 LoopStep 未定义跨事件等待，**不是既定规则**，须用户确认是否应排除外部变化。被抑制事件不能唤醒，且不得补发；无限等待本身不因暂未变化被判 NO_NET_CHANGE。
5. **中断/死亡/资源不足**：保留已经结算的结果，结束当前实例及所有活动轮上下文；沿旧 `_run_loop` 顺序不把未完成轮补判为 `NO_NET_CHANGE`，避免覆盖原先中断原因。显式正常终止是否视为第 3 项退出，按候选规则处理；具体游戏含义需确认。
6. **多区域同一边关闭**：全部候选检查使用该边转移前相同的最终游戏状态及各自独立起点，按编译期稳定定义的优先级顺序（嵌套内到外；非包含交叉区域的次序待确认）执行；首个中断即停，不重复支付或重算效果，诊断记录全部相关区域。

旧标记路径必须逐字节等价于旧 `_run_loop`：检查施法者 → `spell_loop_guard` → 定次/提交上限 → `LOOP_GUARD` → 轮初快照/计数 → 体 → 已中断则退出 → 检查无动作或前后指纹相同 → 下一轮。guard 在定次上限之前；定次结束不额外生成空轮。工程安全阀现状是明确的 `loop_guard` 中断，本轮按用户要求保持现状，不将之标成游戏规则，也不引入可继续的替代行为。

### 图示例（均为设计示意，不是现有可执行 DSL）

- **多回边**：`A(条件)→B(动作)→C(条件)`；C 可回 A，也可到 `D(动作)→A`。C→A 和 D→A 都结束一次 A 区域的轮；实际只沿一条边发生一次检查。
- **嵌套**：`A(外条件)→B(内条件)→C(动作)→B`；内条件不成立 `B→D(动作)→A`，外条件不成立 `A→结束`。B 的每个完成轮独立检查；其效果包含在 A 的轮初到轮末状态里，A 回边再检查一次。B 首次条件不成立时，没有进入内轮，不把这一状态当作空轮。
- **交叉/多入口**：`入口→A或B；A→B→C；C→A或B或结束`。A→B→C→A 与 B→C→B 重叠，B 可从外部进入。不能仅因交叉拒绝；若第一次 A→B→C→B，候选协议在 B 回访时闭合 B 区域，在后续 C→A 时闭合 A 区域，各用自己的轮初；若事件/中途退出导致两个重叠区域同时关闭，则按前述未决规则确定唯一顺序，不以 DFS 顺序暗定。此例需实际编译/运行测试证明，当前只是可行方案，不声称已经支持所有变体。
- **中途退出**：`A→B(动作)→C(满足退出?)`；成立→区域外 E，不成立→A。候选协议在 C→E 前以 A 的轮初和当前状态检查；若 E 不是循环一部分，E 的效果不会追溯计入该轮。若 B 被规则判为跳过且没有净变化，则该实际进入的部分轮如何对待须通过本轮候选语义确认；旧法术维持旧行为。
- **等待事件**：`A→B(动作)→W(等待合法事件)→C(条件)→A/退出`。W 挂起期间不完成一轮；合法事件恢复后到回边或退出边比较 A 轮初与当时的战场。由反应限制抑制的事件不能令 W 恢复，也不会事后补发。
- **状态变化后重新判断**：`A(生命>30?)→B(合法燃命)→A`，每次到 A 按当前状态重新判断；若实例开始前该条件已有合法事件级冻结，则按原冻结规则，而非强制动态。回边要先完成上一轮的净变化检查。

## 6. 事件自触发与重入

事件事实（来源、目标、时点、event_id/parent_event_id、事件上下文及实际结果）与触发候选、窗口许可、执行实例分开记录；仍通过已有战斗事件/监听机制，不用全局新队列重排时序。事实存在不代表可触发或可恢复等待：必须同时经过触发匹配和既有窗口/重入许可。**等待节点和普通跳转都不得绕过重入限制；被抑制的事件不得唤醒等待，也不能擅自补发。** 事实是否仍进入失血等账本按原结算路径处理，不等同于允许开启窗口。

旧标记迁移的回边是当前实例内按旧轮数、守卫和日志继续；真实事件触发另一个实例是不同机制。原实例是否进入下一轮仅按既有循环规则与已迁移的旧执行语义判断；不能因等待节点观察到一个被抑制的事件而续跑，也不能伪造事件。血炼周天的反应内部失血遵守现有抑制，旧实例由兼容流程推进。新法术在无旧标记时，具体如何证明终点事件符合循环法则且允许本实例继续、避免重复计轮，仍需在不放宽重入的前提下对规则和测试作进一步确认，不能默认为立即递归或补发。

### 动态判断、冻结和重放：源码时间线

1. `SpellExecution.__init__` 把 `request.branch_snapshot` **复制**成 `_frozen_at_start`，`_run_decisions` 初始化为空；该副本在本次常规执行中不会因为首次判断而更新。
2. `_run_if` 通过 `_index_ifs` 的路径取冻结值：若该路径已经存在于 `_frozen_at_start`，使用它而不求值；否则调用 `_evaluate_spell_condition`，并用 `_run_decisions.setdefault` 仅记录这一节点在本次执行的**首次**结果。下一次到达同一未冻结节点时仍从当前状态重新判断，首次记录不会反过来冻结当前实例。条件求值失败按现有 FAILED 行为处理。
3. `_drive` 完成 `_run_steps` 后，用 `setdefault` 将首次结果写到 `request.branch_snapshot`；`_run_flow_spell` 和道纹前触发路径在原 decision 尚无快照时将结果与 `_engine_branch_owner` 写回提交。之后复用同一 decision 的新执行实例，才会在启动时把已有分支选择放进 `_frozen_at_start`。已有快照不会因后续状态变化被覆盖；未到达过的节点不必凭空写入。具体异常提前终止到哪个位置的写回，以实际 `_drive` 退出路径为准，不泛化为所有失败都会写回。
4. 暂停保存记录 `results`、`run_decisions` 和请求等。`restore_paused` 为重建生成器，将保存的 `run_decisions` 同时赋给 `_frozen_at_start` 和 `_run_decisions`，开启重放，从头驱动旧控制流；`_run_action` 按 step_key 和 iteration 取历史结果，不支付、不调用单步效果或 `on_step`，不对已经重放的轮应用当前指纹比较。结果重放完后恢复实时执行。
5. **重要现状与风险**：历史只按节点保存首次分支，而非逐次判断轨迹；若某条件在单实例循环里先真后假，重放时该节点可能被首次结果固定，导致步骤键不一致或重建错误。本轮用真实 CombatEngine、燃命和再生构造两轮执行，得到 `(燃命, 槽0, 第1轮)`、`(再生, 槽1, 第2轮)`，随后直接调用 `restore_paused`，实际报 `ValueError: 施法存档步骤错位: 记录1/2，控制流0/2`。这是执行器级探针，不是磁盘存读档端到端测试，也不证明所有旧档失败。重放结束后 `_frozen_at_start` 仍被置为 `run_decisions`，其对后续动态判断的影响也需实测。新架构须保存按次轨迹和原启动冻结表，不能把首次判断一律冻结；旧暂停档的信息不足处理须兼容、安全且明确。

## 7. 暂停、存档与重放

新帧保存 PC（下一个待执行节点及“动作已结算/正在等待对手/等待事件”等阶段）、程序版本/哈希、每个循环上下文的轮号和轮前指纹及已执行基线、事件/窗口/反应上下文与所有权、事件等待令牌及去重信息、冻结映射、**按访问次序的条件选择轨迹**、原动作槽决策、步骤结果、目标引用、支付与回调阶段、临时授权资源和调度优先级。全部数据必须可序列化，避免存活引擎、生成器或实体引用；版本不匹配、节点缺失、轨迹不一致时拒绝恢复而不部分变更。

新版本可用显式 PC 直接恢复，但要有完整可核验轨迹以审计；旧档通过旧适配器恢复历史 AST/步骤及快照，再映射到编译图。仅凭每个条件节点的首次选择无法推断同一节点在循环不同时刻的历史选择；对信息不足的旧暂停档不能静默猜测或重做历史效果，需先通过真实旧档验证可恢复范围，必要时停留旧执行器完成该实例或拒绝并解释（迁移方案待验证）。新记录的重放只读取历史轨迹，不调用支付、动作结算、回调或触发；重放结束后从 PC 对尚未完成的条件动态求值。交易回滚、预演沙盒、嵌套法术栈、黄符/协力临时道纹、随机状态和事件令牌均需同等覆盖。保存版本升级必须提供旧存档兼容，不可仅 bump 版本丢弃已有档案。

- 真实战斗：局部/全局/兄弟/嵌套循环及循环内状态变化；逐层净变化、零进展、累计回复但面板净零、资源与目标失效、闪避与失败区别、已完成步骤保留，检测同拍离场优先；异常回滚和对手空档保持原样。
- 事件：攻击显式和非攻击自动反应、多个候选完成次序、同类反应嵌套抑制、不同合法事件互相触发、事实入账但不补发、无真实事件不自触发、血炼周天按旧循环路径多轮，另单测自动路径上限和触发条件。

- 入口：单纹、瞬发、定义并触发、预定义、协力、黄符、受束缚、敌方/盟友、自定义资源、预演、失败回滚和旧 API 用真实游戏测试，阶数与各路径出手照现有规则；最后跑全部 pytest。

## 9. 未决规则与实施门槛

1. 旧显式循环与自然事件循环同时存在的法术如何防止同一事件造成额外一轮？兼容期旧标记不引入新的重复，非旧流程需定义候选身份及去重键。
2. 无标记的新流程末尾产生启动事件但当前反应窗口禁止重入时：是否可在原实例进入下一轮、被重入限制抑制时不可供等待节点绕过限制，也不得补发；原实例仅按既有循环规则决定是否继续。需细化未被抑制时的同事件去重与下一轮判断。
3. 自动反应（例如非攻击失血的血炼周天）当前一轮上限暂保持现状；是否将来修改、以及它是否为规则，需进一步对照事实后另行裁定。
4. 任意跳出循环、终止当前法术、事件等待跨时间或外部行动改变状态时，轮末如何界定、净变化比较包含哪些变化？旧 LoopStep 未覆盖这些新结构。
5. 对可确定轮次的多入口/交叉循环应支持；对多个合法环分解及同边关闭多个重叠区域，需要确认入口选择、检查顺序和去重语义，不能以严格嵌套作为上限。
6. 正文施法费用与事件法术目前不扣主动步骤的口径如何解释；本轮及迁移兼容期维持现状，不隐式改变。
7. `battlefield_fingerprint` 的枚举与“所有状态”之间具体缺漏需逐项对照裁定；技术阀触发时本轮保持现有 `loop_guard` 中断。
8. 需要更精确地核对事件等待可选时机、主体身份、被抑制事件是否可见、跨战斗生命周期，以及旧暂停档历史分支信息不足时的迁移策略。

下阶段先完成多入口及交叉图轮次的形式化推演，以及事件路径/自动反应、真实旧档及指纹差分的专项核对，给出上述分歧对照和选择；不将待确认项当作游戏规则。完成设计评审和所需裁定，再以小批次接入、测真实结算并迁移旧路径。
