# 法术统一流程架构方案（设计稿，待规则确认）

本稿依据仓库代码、规则正文和测试的已核查部分，以及用户本轮五项决策制定；不是功能已实现的声明，也不声称完成全仓穷尽式审查。本轮只写设计，不修改战斗代码或规则事实源。`spell_program.py` 是此前提交的静态结构草案，尚非下述完整方案，更未接入生产执行。

## 1. 目标与不变量

对外提供单一施法行动；逻辑基础为已有道纹动作、条件、流程控制和事件。顺序是默认边，分支和重复由条件及边构成；循环区域及其上下文只属于编译/执行内部元数据，不向玩家暴露 LoopStep。所有实际动作继续调用 `engine/combat_parts/spells.py` 的法术单步结算核心及既有道纹前置、资源支付和伤害机制；不能由图解释器直接更改状态。主动/反应路径的 `SpellStepPolicy`、行动支付、反应窗口、顺序、阶数、目标、X、异常与中断、X=0 及原有定义生命周期都保留，除非用户另作规则裁定。

现有 `use_daowen`、`define_spell` 和 `cast` 的兼容入口不可在迁移中删除；面向玩家的统一入口是独立后续阶段，转接后也需保持同样的参数校验、事务回滚、束缚和决斗优先权。仅合并展示不能称作底层统一。

## 3. 描述层、图结构与旧 DSL 迁移

程序定义 = 稳定 `program_version/program_id` + 启动配置（瞬发或既有合法事件、持有者/角色与触发上下文）+ 有序节点表 + 显式入口 ID + 旧源映射和版本化编译元信息。ID 由定义提供或编译器依据旧 AST 持久生成，**一旦签发不可因插入而重编号**；旧 AST 的路径仅作为首次转换的兼容映射，不承诺重新编译不同文本得到相同 ID。禁止重复/空 ID、缺失目标、非法节点/条件与无法确定的流程，完整验错且不改战斗状态。

- 动作节点：`{id, action: 现有 ActionStep 或等价类型, next?}`；声明目标角色及决策槽映射，未设 next 即后继。执行时依现有 policy、实际角色/目标和 StepRequest 调用单步结算；动作完成、闪避、跳过、失败、中断分别沿原协议处理。空档/支付仍由原调度负责。
- 条件节点：`{id, expression: 现有 Cmp/BoolOp/Not AST, true?, false?, policy}`；两边均指合法节点或定义为默认后继，分支可汇合、跳过任意范围、嵌套或回跳。表达式和可读取字段仍经现有 resolver、事件身份与合法性校验。
- 跳转/终止：`{id, target}` 或结束；无条件跳转亦经同一图边转移与循环/窗口限制。默认顺序是显式编译得到的后继边，图构建后运行时不按数组下标算跳过数。
- 事件等待：`{id, event_selector, resume}` 仅接入实际已接线的事件源、合法身份与既有窗口策略；事件名称、主体和上下文可匹配，等待不合成事件、不支付道纹成本。事件是否到达、被既有重入策略抑制以及该等待是否可恢复由事件层判定，不能单靠程序计数器强行继续。可监听范围、取消与事件投递规则见待确认项。

迁移表：

| 旧组件 | 新表示 | 必须保留的元数据 |
|---|---|---|
| 顺序 ActionStep | 动作节点 + 默认顺序边 | DFS 槽号、目标角色、X/闪避/附加决策和步骤日志 |
| IfStep（含嵌套、空否则） | 条件节点 + 真/假边 + 汇合目标；空分支直达汇合 | `_index_ifs` 旧路径到节点 ID 映射、条件首次选择、冻结范围、两臂槽顺序 |
| LoopStep/`循环N次` | 普通回边 + 编译产生的内部循环区域 | 旧体边界、前置 `spell_loop_guard`、每轮快照、定次/请求上限较小者、已执行数、工程阀、循环结果及日志轮号；**不是无条件无限跳转** |
| tuple 内置流程 / `loop=True` | 兼容适配到动作/边；已有定义的触发配置原样保留 | 旧内置定义、完成顺序、循环停条件、旧 flow 的决策布局 |
| 触发时机 / 瞬发 | 注册于既有触发层 / 主动入口 | 时机接线状态、持有者、来源、调用策略及事件上下文 |
| `SpellCastRequest` | 同一动作节点映射槽，沿用一次提交一槽 | 未走分支也保留槽，循环各轮沿用对应决策；`max_iterations`、`source`、branch_snapshot |
| 阶数 | 基于源级语义的静态元数据 | 触发算一重，瞬发不算，动作每处一次、两分支均计，循环回边不计；不能按运行步数/编译插入的跳转数计算 |

迁移先在影子编译中比对旧 AST 和 CFG 的动作/分支/循环/日志映射；生产始终只用一个可观察的 `SpellExecution` 路径。只有所有受影响调用者（schema、条件预测、目标、协力、自动决策、校验、档案、AI）接入 IR 且差分通过后，才移除旧 AST 执行解释；不能永久并行两套互不兼容执行系统。

## 4. 条件、执行位置与普通跳转

帧包含 program 版本/hash、当前节点 ID、步骤决策及其源、施法者/事件身份引用、policy、执行状态、中断原因、提交冻结表、每次判断轨迹、循环上下文栈、已执行结果、等待令牌和反应/空档上下文。执行器按当前节点取指，检查施法者仍可行动及既有前置，只有动作节点执行效果。一个节点执行完后转移 PC；失败保留原规定的已发生结算，非法图在执行前拒绝。动作消耗及窗口/中断不能由跳转或条件节点重复触发。

动态条件每次到达节点，读取当时规定的 `GameState` 和本次合法事件上下文，条件再到达则重新计算。冻结条件按**提交和执行实例**实现现有语义：启动实例时取得提交中已有的冻结映射；映射已有的节点直接使用，未有的节点在本次执行中每次动态求值，同时只记该节点的首次结果；执行结束将首次结果填入该提交以供后续命中复用。冻结表的来源、归属和生存期沿用同一 decision 的现行语义，不扩大到所有事件或整个战斗。事件完成顺序与触发提交的归属不因节点跳转改变。

## 5. 循环区域编译与每轮检查

编译器在可达 CFG 上建立前驱/后继及支配关系，识别满足**单入口可归约**条件的自然循环：回边指向支配源的入口，关联该入口的区域；进一步构造区域包含树。多个互不相交循环分别作为兄弟，内层区域严格包含于外层；多个回边指向同一入口需合并为一个区域且唯一轮次边界可识别。逐边验证入口、回边、退出目标和区域嵌套；多入口不可归约环、互相交叉而不形成包含关系、不能确定一轮结束的回边组合在验证期报错，指出相关节点与边。不会静默更改为单一循环或交给执行时猜测。明确可支持图的这一限制，不能声称所有任意 CFG 已支持；扩展前仍允许使用多个独立或严格嵌套循环表达复杂流程。

每次进入循环入口时建立独立上下文：区域 ID、活动轮次、起始 `battlefield_fingerprint`、本轮动作执行计数基线、旧/新循环限制和调用上限、退出/中断原因；内外层各自维护。兼容旧标记时严格在旧 `_run_loop` 的顺序执行：施法者存活 → `spell_loop_guard` → 定次与提交上限 → 明示工程阀 → 轮次递增 → 起始指纹/已执行数 → 运行体 → 若中断不假装正常结束 → 完成整轮后判断无动作或指纹相同则 `NO_NET_CHANGE` → 再检查下一轮入口。注意旧 guard 比定次上限更早，避免迁移改变优先次序。

拟在每次回边完成当前轮比较，然后重置该区域快照开始下一轮；退出边在完成完整一轮后也须比较（旧 LoopStep 在体结束时比较，即使下一轮会因定次上限结束）。提前终止、跨区域跳出以及等待事件横跨回合时，何时算完整轮、外部事件状态是否计入，现行规则没有为一般 CFG 明确规定：在获得裁定前对应新图不得宣称已实现该语义，旧图沿用旧规则。嵌套时每次完成内层轮只结算内层检查；外层结束时再检查外层从其独立起点到终点的净变化，内层效果自然包含在外层快照差中；内层中断沿既有中断传播。规则的 `NO_NET_CHANGE` 与工程步数/迭代阀必须是不同原因和可见记录；技术阀不能伪装成规则，当前旧执行器的 `LOOP_GUARD` 停止行为在兼容期保留，未来能否暂停并继续需另议。

## 6. 事件自触发与重入

事件事实（来源、目标、时点、event_id/parent_event_id、事件上下文及实际结果）与触发候选、窗口许可、执行实例分别记录；来源仍为现有战斗事件/监听机制，保持其先后次序，不能把所有事件一律放入全局队列重排。事件发生不等于必定开窗；上下文和事件主体必须满足启动条件，再应用现有完成顺序、反应策略及重入抑制。普通 PC 回跳只能重复已在运行的流程，不能伪造事件或放宽重入。

两种不同的“再执行”：旧标记迁移的回边继续当前实例，根据其原轮数、守卫和日志运行；真实事件满足启动条件则按既有事件路由和是否允许开窗决定是否建立新实例。若事件在反应内部产生而当前钩子抑制反应，依旧不递归开窗，也不自动补发；其事实仍由对应既有失血账等记录。如何在不突破此限制的前提下，将“末尾真实事件”用于未带旧标记的新法术下一轮，及允许/拒绝哪些等待监听，不从正文擅自推断，列入待确认和实测。血炼周天旧实例通过迁移后的旧循环区域继续而不是通过递归窗口再次触发；非攻击自动上限必须保留并另行确认。

## 7. 暂停、存档与重放

新帧保存 PC（下一个待执行节点及“动作已结算/正在等待对手/等待事件”等阶段）、程序版本/哈希、每个循环上下文的轮号和轮前指纹及已执行基线、事件/窗口/反应上下文与所有权、事件等待令牌及去重信息、冻结映射、**按访问次序的条件选择轨迹**、原动作槽决策、步骤结果、目标引用、支付与回调阶段、临时授权资源和调度优先级。全部数据必须可序列化，避免存活引擎、生成器或实体引用；版本不匹配、节点缺失、轨迹不一致时拒绝恢复而不部分变更。

新版本可用显式 PC 直接恢复，但要有完整可核验轨迹以审计；旧档通过旧适配器恢复历史 AST/步骤及快照，再映射到编译图。仅凭每个条件节点的首次选择无法推断同一节点在循环不同时刻的历史选择；对信息不足的旧暂停档不能静默猜测或重做历史效果，需先通过真实旧档验证可恢复范围，必要时停留旧执行器完成该实例或拒绝并解释（迁移方案待验证）。新记录的重放只读取历史轨迹，不调用支付、动作结算、回调或触发；重放结束后从 PC 对尚未完成的条件动态求值。交易回滚、预演沙盒、嵌套法术栈、黄符/协力临时道纹、随机状态和事件令牌均需同等覆盖。保存版本升级必须提供旧存档兼容，不可仅 bump 版本丢弃已有档案。

## 8. 验证与测试矩阵（预期，不是已通过）

- 图静态校验：重复/空 ID、不存在入口及边、非法条件/身份/事件未接线、不可归约多入口环、交叉区域均提交前拒绝；插入节点不更改显式目标。顺序、真假跳转、跳过、多条件和嵌套分支验证精确 PC 轨迹。
- 旧兼容差分：将全部内置、已定义、自创旧 DSL 编译；比较旧执行与迁移执行的各步骤、决策槽、目标、日志、费用、HP/状态/事件、阶数、中断及结束。比较固定次数、`max_iterations`、循环守卫、无效果和资源不足；旧标记不要求真实自触发事件，确保历史行为不变。
- 真实战斗：局部/全局/兄弟/嵌套循环及循环内状态变化；逐层净变化、零进展、累计回复但面板净零、资源与目标失效、闪避与失败区别、已完成步骤保留，检测同拍离场优先；异常回滚和对手空档保持原样。
- 事件：攻击显式和非攻击自动反应、多个候选完成次序、同类反应嵌套抑制、不同合法事件互相触发、事实入账但不补发、无真实事件不自触发、血炼周天按旧循环路径多轮，另单测自动路径上限和触发条件。
- 快照：单实例多轮分支随状态变、跨命中同提交冻结、不同提交隔离；在改变分支/内外循环后暂停并保存/恢复，比较不间断与恢复的最终状态、每个步骤与支付、所有事件/回调次数；新旧版本档案、非法/损坏轨迹、事务失败回滚及预演不得污染真实状态。
- 工程保护：自跳转/互跳及条件始终成立图必须保证调度可观察、不挂死；区分规则 `NO_NET_CHANGE` 和技术保护；测试无限跳转、前向无动作环、等待取消、重入嵌套；技术保护不可谎称自然规则。执行时间阀是否允许继续另待规则/产品裁定。
- 入口：单纹、瞬发、定义并触发、预定义、协力、黄符、受束缚、敌方/盟友、自定义资源、预演、失败回滚和旧 API 用真实游戏测试，阶数与各路径出手照现有规则；最后跑全部 pytest。

## 9. 未决规则与实施门槛

1. 旧显式循环与自然事件循环同时存在的法术如何防止同一事件造成额外一轮？兼容期旧标记不引入新的重复，非旧流程需定义候选身份及去重键。
2. 无标记的新流程末尾产生启动事件但当前反应窗口禁止重入时：是否可在原实例进入下一轮、事件是否供等待者观察，以及是否需要在窗口结束后保留/丢弃？当前规则不完整；不默认递归，也不默认排队补发。
3. 自动反应（例如非攻击失血的血炼周天）当前一轮限制是否属于应保留的规则，还是旧实现缺陷？先给显式/自动的真实现状，再请用户裁定，不擅自修正。
4. 任意跳出循环、终止当前法术、事件等待跨时间或外部行动改变状态时，轮末如何界定、净变化比较包含哪些变化？旧 LoopStep 未覆盖这些新结构。
5. 新 CFG 含多入口/交叉重叠循环是否允许；本稿暂设计成明确拒绝并诊断，并非声称能表达任何 CFG。
6. 正文施法费用与事件法术目前不扣主动步骤的口径如何统一；不以重构隐式改变。
7. `battlefield_fingerprint` 的枚举与“所有状态”之间具体缺漏需逐项对照裁定；技术阀达到时是暂停可继续还是保留旧中断。
8. 需要更精确地核对事件等待可选时机、主体身份、被抑制事件是否可见、跨战斗生命周期，以及旧暂停档历史分支信息不足时的迁移策略。

下阶段先做事件路径/自动反应、真实旧档及指纹差分的专项实测，给出上述分歧对照和选择；不将这些待确认项当作已经做出的游戏规则。完成设计评审和所需裁定，再以小批次接入、测真实结算并迁移旧路径。
