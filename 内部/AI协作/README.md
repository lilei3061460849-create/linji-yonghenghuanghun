# AI 跨会话协作与长期上下文架构

> 本目录定义 AI 如何读取、引用和维护项目知识，不是新的游戏规则事实源，也不是第二份待办清单。
> 项目正式内容仍由根目录现有事实源负责；GitHub Issues / PR 仍是任务状态唯一台账。

## 目标

让任意具备 GitHub 仓库访问能力的新 AI / 新会话，都能在有限上下文内恢复项目结构、规则优先级、当前任务与历史纠错；需要细节时按索引读取原文，而不是把整个仓库或聊天记录塞进单轮上下文。

## 五层知识模型

| 层 | 内容 | 权威位置 | 使用规则 |
| --- | --- | --- | --- |
| 项目入口 | 仓库用途、文档导航、事实源优先级 | 根目录 `README.md` | 新会话先读 |
| AI 协作契约 | 开工、修改、验证、提交、汇报规则 | 根目录 `AGENTS.md`、`AI_EXPERIENCE.md` | 与其他说明冲突时遵循现行最高优先级协作规则 |
| 正式事实 | 世界观、规则、道纹、物品、法术、副本、引擎与结构化数据 | 见下方事实源地图 | 以各自指定事实源为准，不能用摘要替代 |
| 决策与纠错 | 用户裁定的定位、设计理由、被纠正的错误认知 | 本目录的《设计决策与纠错索引.md》及其指向的正式文件 / Issue / PR | 本索引是导航和必要的纠错提示；不复制整套规则，不覆盖最新裁定 |
| 工作状态 | 待办、实施状态、验证结果、审查入口 | GitHub Issues、PR、Actions | 不在仓库另建 CURRENT_TASK 或平行待办清单 |

## 事实源地图

先读根目录 `README.md` 的「AI / 维护入口」和「文档导航」。常用路径：

- 通用规则：`规则正文.md`
- 世界观正典：`故事文档.md`
- 操作与战报规范：`推演规范.md`
- AI 开发维护、协作和推演约束：`AI_EXPERIENCE.md`
- 引擎架构：`engine/README.md`，具体行为查 `engine/`
- 结构化规则：`data/rules/*.toml`
- 道纹、物品、法术、副本：`全道纹索引.md`、`物品索引.md`、`法术索引.md`、`副本索引.md` 及各副本文档
- 测试证据：`tests/`
- 历史设计依据、已废止假设：`内部/archive/`
- 外部 AI 单文件入口：`AI_CONTEXT.md`，但它是生成聚合物，不是开发事实源

### 事实冲突处理

遵循根目录 `README.md` 与 `AI_EXPERIENCE.md` 已定义的优先级。尤其注意：

1. 用户最新明确裁定优先。
2. 规则与引擎、测试出现冲突时，不得由 AI 自行选择“看起来合理”的一方；按维护规范停止并请求裁定。
3. 生成摘要、速查、角色记忆、遗言和历史档案都不能反向覆盖事实源。
4. 代码现状不自动等于用户设计意图；测试通过也不证明规则解释正确。
5. 不确定某条内容是否已确认时，标记为待核实并回到来源，不补造限制。

## 新会话启动协议

1. 确认仓库和默认分支，读取根目录 `README.md`、`AGENTS.md`。
2. 读取本文件与《设计决策与纠错索引.md》。
3. 读取 `AI_EXPERIENCE.md` 中相关协作规范、最新裁定和当前有效约束；不要无差别吞入整份长文件。
4. 检查 GitHub 当前打开的 Issues、PR 和最近相关 Actions。Issue 是待办状态唯一台账；PR 是当前实现与验证交付记录。
5. 根据用户本轮目标，从事实源地图读取相关原文、引擎实现和测试。不要只依赖 `AI_CONTEXT.md`。
6. 回答前区分：已确认、已实装、待实装、待讨论、已否决。没有证据的状态不得猜测。
7. 若要修改，遵循 `AGENTS.md` 的分支、PR、备份、最小修改和验证要求；修改前检查远端最新状态，避免覆盖新提交。

## 记忆状态标签

- **已确认**：用户明确裁定或认可；若属于正式规则，必须定位其正式事实源。
- **已实装**：当前代码 / 数据确实实现，并有可核查的实现位置；测试状态另行说明。
- **待实装**：设计口径已确定，但尚未进入正式实现。不得描述为当前可用机制。
- **待讨论 / 待裁定**：用户尚未作出最终决定；通常由 GitHub Issue 跟踪。
- **已否决 / 已废止**：明确不采用或被新裁定替代；保留纠错提示，不能继续作为现行方案。
- **历史记录**：仅说明过去发生过什么，不构成现行规则。

标签可以组合，例如“已确认、待实装”。“已确认”不等于“已实装”，“已实装”不等于“已通过全部验证”。

## 决策、纠错与历史

- 用户明确裁定的长期口径：在《设计决策与纠错索引.md》保留简短索引，详细规则仍只写在对应正式事实源。
- AI 自己曾经犯过、且可能反复犯的错误：记录错误认知、正确边界、权威来源和禁止推断事项。
- 被替代的完整方案或技术证据：放入 `内部/archive/`，并标注历史 / 废止状态。
- 尚未裁定的设计问题：开 GitHub Issue，不把猜测写成决策。
- 普通对话、临时推演、未获用户确认的建议，不自动升级为项目设定或长期决策。

## 跨会话交接

不新增仓库内的 `CURRENT_TASK.md`。任务状态继续只在 GitHub Issue / PR 中维护，避免与 README 和 AI_EXPERIENCE 已有文档分工冲突。

交接时使用《会话交接模板.md》整理内容，并放入对应 Issue / PR 描述或评论：
- Issue：目标、范围、验收条件、待裁定事项。
- PR：当前改动、基线、测试命令与真实结果、未完成项、风险。
- Commit：可追溯的实际文件变更。
- Actions：自动化验证的首要证据。
只有无法由 Issue / PR / Commit 表达的长期技术知识，才新增独立文档。

## AI 修改与 GitHub 交付规则

1. 先读当前文件、来源文件、相关调用方和测试；先查 Issue / PR，避免重复任务。
2. 用户明确要求的范围优先；不擅自扩大目标，不把推断写成裁定。
3. 修改前标明文件的角色：事实源、生成物、索引、协作说明、历史档案或运行时代码。
4. 禁止手改生成物。尤其 `AI_CONTEXT.md` 必须由 `python3 sim/gen_ai_context.py` 生成，并用 `--check` 验证。
5. 正式规则变更必须沿事实源 → 引擎 / 数据 → 测试 → 派生文档链路处理；本架构文档变更不得顺带修改游戏规则。
6. 遵循根目录 `AGENTS.md`：使用会话工作分支、开 PR、分段提交、不得擅自合并 main；不得覆盖用户未提交或他人新提交的改动。
7. 每个独立改动后核对 diff、文件完整性和引用；按影响范围执行定向测试。全量测试只在适当的批次收尾执行。
8. 只报告实际运行的测试和可核查结果；未运行写“未运行”，失败写明失败，不推测通过。
9. 提交信息说明变更目的；PR 描述关联 Issue、基线、改动范围、验证结果和未完成项。
10. 交付时列出文件、Commit、PR、测试证据，以及明确未做的事情。

## 本次架构边界

本架构只增加 AI 协作与上下文管理文档，不改变任何游戏规则、世界观、引擎行为、数据或测试预期。若后续发现本文件与根目录 `AGENTS.md` / `AI_EXPERIENCE.md` 冲突，以现有高优先级规范为准，并修订本文件，不反向覆盖原规范。
